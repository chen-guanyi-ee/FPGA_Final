1280x1024 experiment: temporarily abandoned
---------------------------------------------
- A 1280x1024 @ 60 Hz experiment raised the shared pixel/core clock from 65 MHz
  to 108 MHz and updated VGA timing, projection centres, HUD placement, UART
  timing, and the light-gate divider width.
- The experiment completed synthesis, placement, physical optimization, and
  routing, but did not meet timing. The final routed result was WNS -3.828 ns
  and TNS -3236.937 ns; hold timing passed with WHS +0.012 ns.
- This was not a small isolated miss. At a 9.259 ns clock period, the worst
  setup path needed roughly 13.087 ns, corresponding to only about 76 MHz.
  Violations were widespread through shared physics/referee control and data
  paths, so another implementation directive or seed was not a credible fix.
- The attempted timing repairs (extra HUD pipeline stage, renderer delay change,
  mul_pipe hierarchy preservation, and aggressive implementation directives)
  were insufficient. No 1280x1024 bitstream was generated or programmed.
- Active source has therefore been returned to the prior XGA configuration:
  1024x768 @ 60 Hz, 65 MHz, negative XGA sync polarity, 512/384 projection
  centre, XGA HUD coordinates, original one-stage HUD alignment, and original
  48-cycle shot-gate divider.
- The failed experiment remains archived in build_sxga/, build_sxga_impl.log,
  and scripts/synth_sxga.tcl for diagnosis only. It is not the active release.
- Do not resume 1280x1024 on the current shared-clock architecture. Reconsider it
  only with a real two-clock/framebuffer architecture or with physics/referee
  moved to a slower clock domain and proper clock-domain synchronization.

Physics architecture change
---------------------------
- Each logical ball record is 225 bits: x, y, vx, vy, wx, wy, and spin are
  seven 32-bit fields; active is one bit.
- The two GAME/PRED state banks retain true-dual-port BRAM storage for the seven
  numeric fields. The active bit uses the existing asynchronous FF mirror,
  removing one mostly-empty RAMB18 from each bank.
- BRAM lanes use write-first behavior based on the AMD UG901 coding template.
- physics_core now has two local 225-bit records, work_i and work_j.
- Reads are explicitly staged as LOAD -> CAPTURE -> EXECUTE. Partial updates are
  applied to the working records and committed to BRAM separately.
- Arithmetic no longer directly consumes the wide GAME/PRED bank selection or
  read-after-write forwarding network.
- The old previous-cycle and current-cycle 225-bit forward_word mux layers were
  removed from the main arithmetic path.
- The extra stages trade latency for less LUT logic, lower routing pressure, and
  better timing margin.

  full-board-validated release.

Recommended next steps
----------------------
1. Run the full system, referee, quick, camera, and VGA regressions against the
   working-record RTL; physics-only regression has already passed.
2. Review the 80 DRC warnings, especially CFGBVS/CONFIG_VOLTAGE and RAMB18 async
   control warnings.
3. If all regressions pass, generate a separate candidate bitstream from
   build_physics_opt/routed.dcp or a clean reproducible build. Do not overwrite
   the known-good programmed bitstream.
4. Program the candidate and verify VGA output, COM5 mouse/UART control, GAME vs
   PRED behavior, reset/initialization, and low-camera rendering on hardware.
5. Preserve both report sets because the new result improves LUT/timing but not
   Slice count and increases physics latency.

Rejected/deferred approaches
----------------------------
- DSP48E1 PATTERN_DETECT does not replace a 225-bit bank/forwarding mux; it is
  intended for DSP P-output pattern, saturation, rounding, and terminal-count
  detection.
- Unsafe multicycle constraints remain rejected; constraints must describe real
  latency rather than hide violations.
- Merging GAME and PRED banks remains rejected because prediction would corrupt
  or stall live physics state.
- Merging camera work/commit banks remains rejected because partial updates can
  tear.
- A framebuffer/two-clock architecture remains an option only if the shared
  65 MHz render/game clock becomes limiting.
